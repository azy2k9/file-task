# Backend and file storage options for FileTasks

Research checked **12 October 2026** against current provider pricing, limits, terms, and technical documentation. The target is a private personal app for **1–5 people and about 1–10 GB of documents**. The current data model includes Tasks, Events, Recurrence rules, Occurrences, Reminders, Files, and Attachments; the three clients need the same account and API. Family sharing is outside this initial scope. Prices are public USD before tax and do not include the web domain or optional email/SMS delivery.

## Recommendation

**Keep AWS CDK as the leading option if you want to own the TypeScript backend and use tools you already know.** A lean AWS stack of Cognito, HTTP API, TypeScript Lambda, and DynamoDB remains a candidate; use the selected private R2 bucket for file bytes instead of S3. The AWS-only reference stack with S3 is estimated at about **$0.25/month with 10 GB stored** under the small-traffic assumptions in [the AWS cost model](backend-options/aws-baseline.md); its S3 storage component is about 23¢. That is a comparison baseline, not the planned storage choice. With R2, the API issues short-lived signed upload/download URLs and document bytes travel directly between each client and R2. There is no always-on database, NAT Gateway, or server process in this AWS shape. Check the calculator again for the target region and account; the reference estimate uses `us-east-1` and assumes the shared 100 GB AWS internet-transfer allowance is unused.

**Cloudflare R2 is the chosen object-storage provider** (see [ADR-0002](../adr/0002-use-cloudflare-r2-for-file-storage.md)). Its 10 GB-month free allowance covers the stated initial range, direct egress is free, and its S3-compatible API has a documented TypeScript/JavaScript AWS SDK path. Backblaze B2 and S3 remain comparison points, not planned alternatives for initial implementation. Keep the API contract provider-neutral with opaque object keys so the decision can be revisited later. This selects file storage only; the API runtime, database, and authentication provider remain undecided.

If the priority is a managed TypeScript backend with no monthly floor, the closest options are **Cloudflare Workers + D1 + R2** and **Convex Starter**. Workers + D1 + R2 can fit the storage and low-traffic workload inside its published free quotas, but it needs custom authentication and the current password-hashing flow should be measured against Workers' 10 ms free CPU limit. Convex gives a TypeScript-first managed database and functions, but its free file quota is 1 GB and its standard download URLs are permanent bearer links. Those trade-offs make either option a deliberate runtime and data-model choice, rather than a drop-in hosting change.

If paying for an integrated relational backend is acceptable, **Supabase Pro** is the simplest fit for a separate web client, native clients, private files, and relational data; its production floor is $25/month. **Appwrite Cloud Pro** is another $25/month route with native SDKs and TypeScript functions, but its available UK/EU regions and current quota rules need to match your requirements. See [the managed backend comparison](backend-options/managed-backends.md).

The table separates whole backends from object-storage services. **R2 and B2 do not supply authentication, metadata, or application authorization.** A storage free tier does not by itself make a private Files section secure: the API must check the signed-in user's File/Attachment ownership before issuing an upload or download URL.

Upload services aimed at product teams are a different category. UploadThing's free plan lists 2 GB and unlimited transfers, but its current paid plan is where Private Files are listed; the free tier therefore is not a verified private-document bucket for this app. ImageKit's free plan has 3 GB storage and 20 GB bandwidth, while Cloudinary meters storage, bandwidth, and transformations from a shared credit pool; both products focus on image/video delivery and optimization rather than a complete private-document backend. Those plans can fit some public media use cases, but their headline storage numbers are not directly comparable to a private Files section. ## File handling that works across all three clients

Keep each bucket private. Store a stable, opaque object key and file metadata in the database; do not use a signed URL as the File's identity. A client first asks the API to upload or download a File. The API checks the account and Attachment relationship, then returns a short-lived signed URL for one object and one operation. The browser or iOS/Android client sends the bytes directly to object storage over HTTPS. This keeps large bodies out of Lambda, Workers, and API Gateway, and gives all three clients the same flow. Signed URLs are bearer credentials until expiry, so keep their lifetimes short and never log or save them as durable links.

For browser uploads, configure storage CORS for the real web origin, required methods, and headers. Native HTTP libraries do not enforce browser CORS. Enforce file-size and allowed-content rules at the API and verify uploaded metadata before attaching the File to a Task or Event. If provider-side encryption is not enough and the provider must not see document plaintext, client-side encryption is a separate design requirement; ordinary storage encryption at rest is not end-to-end encryption.

## How to choose

- **Choose AWS CDK** if you value a familiar, explicit TypeScript infrastructure project and want the cleanest independent API contract for the three clients. At this scale, its estimated ongoing bill is about a quarter per month, excluding domain, hosting of the web client, messages, and unusual usage. Use HTTP API + Lambda + Cognito + DynamoDB + S3; upload directly to S3. Add Scheduler/SQS only when reminder delivery is implemented.
- **Choose Workers + D1 + R2** if a free tier and serverless TypeScript runtime are the stronger goal, and you are willing to replace/adapt the existing Node server and own auth. Benchmark the current password hashing before relying on the free runtime; its CPU ceiling is the key risk, not the database size.
- **Choose Supabase Pro** if SQL, transactions, and row-level security are worth $25/month and you want most backend pieces managed together. Keep uploaded bytes private and authorize access with RLS or short-lived signed URLs.
- **Evaluate Appwrite Pro** if its API-first functions/auth/storage model is more appealing than Supabase's SQL-first model. Its public plan comparison is dynamically rendered, so verify the project console quota, Frankfurt/UK availability, and paid add-on behavior before implementation.
- **Consider Convex Starter** if reactive TypeScript data/functions are a feature you want. Decide the external auth issuer and private-file delivery first; the included file quota and permanent default download URLs are material design choices.
- **Use Cloudflare R2 for File object storage** behind the separately selected API. Configure the bucket as private, keep account credentials server-side, authorize each File/Attachment before returning a short-lived signed URL, and configure browser CORS for the web client. R2 is not the API, database, or authentication system.

For reminders, the delivery channel can cost more than the database work: schedule due Reminders idempotently, then budget email/SMS separately. Calendar sync also needs background jobs and provider credentials, but it does not require files to pass through the API. Database records should keep provider-neutral object keys so storage can change without changing the Task/Event model.

## Proposed repository boundaries

The client folders now follow the requested shape:

```text
apps/
  web/       Next.js web client
  android/   native Android client
  ios/       native iOS client
services/
  api/       current API domain/auth/database code; runtime still under evaluation
infra/       future TypeScript CDK or provider-native infrastructure
```

The current issue #2 API route handlers remain as a temporary Next.js adapter under `apps/web/app/api`; the authentication, database, and workspace logic has been moved to `services/api/src`. This keeps the working prototype intact while the server runtime is selected. It is **not yet a separately deployable API service**. Once the backend choice is made, the next architecture step is to put a real HTTP runtime in `services/api`, have `apps/web`, `apps/android`, and `apps/ios` call it directly, and add `infra/` for its deployment resources. The app package and native clients already occupy their own `apps/` directories.
