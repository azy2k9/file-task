# Managed backend options for FileTasks

Research checked **12 October 2026**. Public list prices are in USD before tax. The scenario is a private app for 1–5 people, with roughly 1–10 GB of uploaded documents, a separately hosted Next.js web client and native Android/iOS clients. The product model has Tasks, Events, recurrence rules and occurrences, Reminders, a central File record, and many-to-many Attachments linking Files to tasks, events, recurrence series, or individual occurrences. FileTasks remains authoritative when calendar copies are synchronized outward.

## Recommendation

**Supabase is the strongest whole-product fit if a $25/month production floor is acceptable.** PostgreSQL naturally represents Tasks, Events, Occurrences, Reminders, Files, and Attachment join rows with foreign keys and transactions. Its generated REST API and client SDKs work from a separately hosted web client and native apps; private Storage can enforce the same user JWT and Postgres RLS as the metadata. A single Pro project costs $25/month at the default Micro size because the plan includes $10 in compute credits, and it removes free-project inactivity pausing while including 100 GB storage and 250 GB each of uncached and cached egress. The tradeoff is stark for this workload: the Free project has only 1 GB file storage and can pause after a week of low database activity, so Free is a fit only if the archive stays at or below 1 GB and regular app traffic keeps it active.

**If minimizing steady cost matters more than a relational model, Firebase Blaze is the lowest-friction variable-cost alternative.** It has no base subscription and its client SDKs cover web, Android, and iOS. But Firebase Storage now requires a linked Cloud Billing account even when usage is within an advertised no-cost quota; the always-free Cloud Storage tier is limited to US regions, so do not assume that a UK/EU bucket gets 5 GB free. Firestore is document-oriented, and the billing budget/spend-cap controls do not cap Firestore or Cloud Storage. This means the lowest sticker price comes with the largest billing surprise and data-model tradeoff.

**Convex Starter is the lowest fixed-cost TypeScript option, but its bundled file URLs are public bearer URLs.** At 10 GB stored, its published Starter storage rate is about $0.30/month for the 9 GB above the included 1 GB in US pricing, or about $0.39 at the 30% Europe surcharge, before egress and any other metered usage. Its own docs say `getUrl()` files can be fetched by anyone who has the URL, and recommend Cloudflare R2 for expiring file URLs or an authenticated HTTP Action for per-request authorization. Native iOS/Android clients are available, but native apps need an external OIDC auth provider; Convex Auth itself supports React web and React Native and remains beta. The backend is TypeScript-first but more vendor-shaped than a portable REST/Postgres service.

**Appwrite Cloud Free can hold only the low end of the archive.** Its 2 GB free storage is shared across free projects; free projects pause after one week without development activity, and Appwrite deletes projects left paused for 90 days. Pro is $25/month with 150 GB storage, 2 TB bandwidth, and 5 GB maximum file size. The default TablesDB supports typed rows, row permissions, and 1:1/1:many/many:many relationships. Appwrite now also offers native PostgreSQL: the $10 monthly database credit in Pro covers one entry $10 database tier (1 vCPU, 1 GB RAM, 10 GB database storage), so it does not add a fixed charge above Pro. Unlike TablesDB, native PostgreSQL is a separate engine with direct database credentials and no Appwrite auth/permission layer; expose it through trusted TypeScript Functions or an API. For a UK user, Appwrite Cloud’s Europe region is Frankfurt. Appwrite Start's reduced local-price rollout is for India, with a student tier also available in Nepal, not the UK. [Pro and Postgres credits](https://appwrite.io/blog/post/appwrite-now-speaks-postgresql), [plan quotas and regional availability](https://appwrite.io/blog/post/introducing-appwrite-cloud-start-plan), [paused-project deletion](https://appwrite.io/changelog/entry/2026-06-29).

## Private Files and upload behavior

**Supabase:** Storage buckets are private by default. Upload/list/read/delete are gated by Postgres RLS policies on `storage.objects`; private reads require an authorized user JWT or an expiring signed URL. Files can share the same Postgres identity model as `File` metadata and `Attachment` rows. Free buckets cannot configure a file limit above 50 MB; on paid plans the configured cap reaches 500 GB. Transfer methods are more restrictive: standard upload up to 5 GB, resumable/S3 documented up to 50 GB. For personal documents and PDFs this is ample; if a future import includes very large archives, check the chosen transfer path, since a current feature page also advertises 500 GB support. [Private Storage access model](https://supabase.com/docs/guides/storage/buckets/fundamentals), [size setting](https://supabase.com/docs/guides/storage/uploads/file-limits), [upload method limits](https://supabase.com/docs/guides/troubleshooting/upload-file-size-restrictions-Y4wQLT).

**Firebase:** Storage Security Rules can bind path access to `request.auth.uid`, inspect Firestore membership documents, and enforce size/content type. Client SDK operations are authorized by those rules. The common `getDownloadURL()` method yields a long-lived token URL that is a bearer credential; it can be revoked, but whoever has it can reuse it. For sensitive file delivery, prefer rule-checked authenticated SDK download or an app endpoint that authenticates before signing. Server/Admin credentials do not obey client security rules. [Storage Rules](https://firebase.google.com/docs/storage/security), [download URLs](https://firebase.google.com/docs/storage/web/download-files), [object maximums](https://cloud.google.com/storage/quotas).

**Appwrite:** Files have no access by default; bucket-wide or per-file permissions must grant client access (per-file security is an explicit bucket setting). File tokens bypass normal session authorization and create shareable bearer links with an optional expiry. It also supports SigV4-compatible S3 presigned URLs, which must be generated on a trusted server. Pro storage supports 5 GB per file; Free supports 50 MB. Optional bucket encryption, compression and antivirus scanning are skipped for files over 20 MB, so do not infer those features protect large documents without checking their specific limits. [File permissions](https://appwrite.io/docs/products/storage/permissions), [file tokens](https://appwrite.io/docs/products/storage/file-tokens), [S3-compatible signed access](https://appwrite.io/docs/products/storage/s3), [bucket security limits](https://appwrite.io/docs/products/storage/buckets).

**Convex:** The standard upload URL is short-lived (one hour) and can be issued by a permission-checking mutation; it has no configured maximum size but the HTTP POST times out after two minutes. The download URL is a permanent bearer URL and can only be revoked by deleting the file. For authorization on every download, write an HTTP Action that checks the user and returns the file; Action responses are limited to 100 MiB. Convex docs recommend the Cloudflare R2 component when automatically expiring URLs are needed. Thus Convex is the only option here where the built-in file-serving default is a meaningful mismatch with “private attached documents” unless the app accepts bearer links or adds an explicit serving/storage layer. [Convex file upload](https://docs.convex.dev/file-storage/upload-files), [file privacy and serving](https://docs.convex.dev/file-storage/serve-files).

Select the exact location if residency matters. Pro’s spend cap is enabled by default and blocks quota overage until turned off, but compute billing is not covered by the cap. ## What the 1–10 GB archive means for storage choice

- **Up to 1 GB of files:** Supabase and Convex Free fit the storage quantity, but not necessarily always-on use (Supabase pause risk) or complete app data (database quotas). Appwrite Free fits only with up to 2 GB total across the free org and active development; Google Storage can be no-cost on a suitable US region but still needs Blaze. Convex Free has very low 1 GB egress, so downloading/previewing documents may hit egress before file storage fills.
- **1–2 GB:** Appwrite Free may fit; Supabase/Convex exceed their included file quota. Firebase's new bucket allowance may fit in the US, but location/billing applies. Appwrite also has a single 50 MB Free file cap.
- **2–5 GB:** No conventional file-storage free quota reliably fits this entire range in a UK/EU region across all four. Supabase/Appwrite Pro bundle enough private storage at $25/month; Convex Starter metering is tiny if bearer URL privacy or external signed storage is acceptable; Firebase charges usage by Google Cloud region on Blaze.
- **5–10 GB:** Supabase Pro and Appwrite Pro leave significant headroom and private policy integration. Appwrite Pro caps a single file at 5 GB. Firebase Storage permits large objects but has location-specific pay-as-you-go prices. Convex Starter storage is `9 GB × $0.033 ≈ $0.30/month` in US, `≈ $0.39/month` at the Europe rate, plus egress/metered database/function use; that price excludes any external object store or extra auth service.

There is no generic “database included storage” substitute for file storage here: store file bytes in object storage and only file metadata/associations in the database. This keeps record queries small and lets the product preserve one `File` referenced by multiple `Attachment` rows.

## When external R2 is worth the added piece

R2 (and equivalent object stores) avoids a large BaaS storage/egress bill, but it adds a second authorization boundary. The backend must validate the user and `File`/`Attachment` relationship before minting short-lived upload or download access; web CORS, mobile upload retries, orphan cleanup, object-key migrations, and independent storage backup/retention also become app responsibilities. For the 1–10 GB personal archive, the additional moving part is usually not justified solely by storage price if the user is already on Supabase Pro or Appwrite Pro, where storage and private access are bundled. It becomes attractive when the backend's included storage is exceeded, file egress dominates bills, or Convex's need for genuinely expiring/revocable private links already requires an external object endpoint. The companion [object storage report](object-storage.md) prices R2 and other compatible stores at these volumes; its AWS comparison is in [the AWS baseline](aws-baseline.md).

For Firebase, Cloud Storage is already a separate Google Cloud object service integrated with Firebase Auth/Rules, so R2 is not automatically a simplification. For a Firebase app, only add R2 after a concrete storage/egress or portability problem appears. For Supabase, Appwrite or Convex, keep database records backend-agnostic by storing an opaque `storageProvider` + `objectKey` (or a File storage locator) rather than a permanent download URL; signed URLs should be generated on demand and never be the File identity.

## Reminder schedules and calendar sync

All four platforms can run scheduled backend logic: Supabase Cron can invoke SQL or an Edge Function; Firebase `onSchedule` provisions a Cloud Scheduler job; Appwrite Functions support a one-minute cron interval; Convex supports cron and durable scheduled functions. For recurrence, retain the recurrence rule and next due time in FileTasks, then have a small periodic worker claim due reminders and write notification work to an idempotent outbox. Recompute or cancel due work when a series rule, time zone, exception, or reminder changes. This keeps the domain recurrence authoritative and avoids tying each event instance to one provider's job record or scheduler limits. [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart), [Firebase scheduled functions](https://firebase.google.com/docs/functions/schedule-functions), [Appwrite Functions schedule](https://appwrite.io/docs/products/functions/functions), [Convex scheduling](https://docs.convex.dev/scheduling/overview).

Google Calendar and Apple Calendar sync remain app-owned for each provider: none of these backend products implements FileTasks' recurrence/exception semantics, OAuth consent, token refresh/revocation, or reconciliation by itself. Keep FileTasks authoritative and store provider event IDs, sync versions, and encrypted provider credentials behind the backend; sync copies idempotently and record retries/conflicts. This follows the existing rule that calendar entries are outward copies, not the source of event or attachment data.

## PocketBase as self-hosted alternative, not managed BaaS

PocketBase is a single executable with SQLite, built-in auth, REST-ish APIs, realtime, and file handling—not a managed Cloud alternative. It can be inexpensive on a small VM, but the operator owns uptime, OS/runtime updates, backups, object storage capacity, restore drills, and any scaling/HA decisions. Its current official docs list v0.40.5 and state that before v1.0 full backward compatibility is not guaranteed and it is not recommended for production-critical systems unless the operator is willing to follow changelogs and apply migration steps. That maintenance obligation directly conflicts with “managed backend.” [PocketBase overview/status](https://pocketbase.io/docs/), [production/backups](https://pocketbase.io/docs/going-to-production/).

PocketBase exposes ordinary REST API rules that can scope records to users and supports protected files with a short-lived file token (roughly two minutes), validated through the related record’s View API rule. Local filesystem storage is the default; it can use S3-compatible storage when disk is insufficient. Its official JS hooks are an embedded Goja/ES5-flavored JavaScript runtime, not Node and not TypeScript (TS must be transpiled to JS); custom backend code can alternatively be written in Go. Its official client SDKs are JavaScript and Dart, not a first-party native Swift/Kotlin pair, so native apps can call REST or rely on community clients. This does not meet the preference for a managed, TypeScript backend as well as the four cloud services. [Protected file handling](https://pocketbase.io/docs/files-handling/), [embedded JS runtime/TypeScript limitation](https://pocketbase.io/docs/js-overview/), [supported SDKs and REST guidance](https://pocketbase.io/docs/how-to-use/).

## Assumptions and verification gaps

- Allowances are current public plan amounts checked 12 October 2026, not contractual guarantees. Providers can change pricing, and usage is generally aggregated at the plan/org/project scope stated above.
- “File storage” means object bytes and not Postgres/Firestore/Convex metadata or backups. The 1–10 GB estimate does not imply monthly downloads equal stored bytes; file preview/download traffic is a separate egress driver.
- Firebase's product pricing grid currently lists a 5 GB-month allowance for `*.firebasestorage.app`, while Firebase's location docs say Google Cloud Storage's Always Free tier only applies in three US regions and buckets elsewhere follow GCS pricing. The location docs are the safe basis for a UK/EU budget; confirm the console estimate at bucket creation before relying on any new-bucket no-cost quota.
- Supabase upload pages currently disagree at the very high end: configured paid global size is 500 GB, an upload troubleshooting page states 50 GB for TUS/S3, while a newer feature page advertises 500 GB via a storage-specific host. This report treats 50 GB as the conservative supported path and says to verify before relying on >50 GB. No ordinary personal PDF depends on that limit.
- Appwrite pricing is currently split between a dynamic plan comparison and billing docs. This report uses the live pricing page and 2026 Appwrite announcements; its budget cap contains add-on overages but does not include the recurring plan fee, and reaching it may halt API/function/storage operations. The storage quota now also counts Functions/Sites deployment artifacts.
- No platform here implements Google Calendar or Apple Calendar sync for FileTasks out of the box. Those integrations still require app-owned OAuth, provider-token lifecycle/storage, idempotent synchronization, and retry logic. Keep FileTasks' events/files authoritative and treat remote calendar entries as copies.
