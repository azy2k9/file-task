# Private object storage options

Research checked **12 October 2026** against provider pricing pages, official docs, and AWS's published price list. The product glossary calls an uploaded document a **File**; this report concerns its private object bytes, not the File/Attachment metadata or the rest of the backend. The intended first workload is 1–5 people, each with a separate private account, and roughly 1–10 GB of files in total; future family sharing is outside this comparison. Scenarios below show growth and egress costs.

## FileTasks decision

Cloudflare R2 is selected for File object storage; the decision and its consequences are recorded in [ADR-0002](../../adr/0002-use-cloudflare-r2-for-file-storage.md). The comparison below remains useful for cost and migration context. This does not select the API runtime, database, or authentication provider. “AI-friendly” is treated here as an inference about R2's familiar S3 API, published integration examples, and AWS SDK support, which make implementation and troubleshooting accessible to TypeScript developers and AI coding tools; it is not a special AI product feature.

## Findings for the initial workload

Cloudflare R2 and Backblaze B2 each publish an ongoing 10 GB storage allowance; both also have enough free requests for the examples below, and both make direct downloads free at these volumes. Tigris offers an ongoing monthly 5 GB allowance, 10,000 Class A and 100,000 Class B requests, and no card to start. Its public docs do not verify CORS for browser requests to private buckets; its current terms leave some uncertainty about ordinary app-user access to private personal files, and its DPA cautions that the service is not intended to meet legal obligations for sensitive data. AWS S3 is the familiar reference and can be used independently of the Next.js client, but its new-account offer is time-limited credits rather than an enduring S3 storage tier; its direct Internet egress becomes the largest cost in the 1 TB example.

At the top of the stated initial range, 10 decimal GB stored steadily is still within R2's and B2's published 10 GB storage allowances. With Tigris's binary unit, 10 decimal GB is about 9.31 GB, so storage just above its 5 GB free allowance is about $0.09/month; its normal request allowances and direct egress remain free at personal-use volumes.

These are **object-storage subtotals only** (stored bytes, listed object requests, and direct Internet downloads). They are not estimates for a complete backend: database, API/compute, identity, domain, monitoring, backups, taxes, and any extra network services are excluded.

## Private uploads/downloads from Web and native clients

All four products can be accessed independently of a Next.js-hosted client. The practical private-file pattern is a private bucket plus a separately hosted backend that authenticates the person, checks that person can access the File, and then issues a short-lived signed URL for one object and one operation. The browser or iOS/Android app transfers bytes directly over HTTPS to storage. Keep long-lived storage credentials only on the backend: a presigned URL is a bearer credential for its signed operation until expiry. This pattern is documented for [R2](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [B2](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api), [Tigris](https://www.tigrisdata.com/docs/objects/presigned/), and [AWS S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html).

R2, B2, and Tigris accept the AWS S3 SDK for JavaScript with provider-specific endpoints/credentials; AWS S3 uses its native endpoint. For R2, the documented JavaScript SDK configuration uses `@aws-sdk/client-s3`, the account endpoint, and region `auto`. R2 presigned URLs authorize GET, HEAD, PUT, or DELETE for one object, with expiry from 1 second to 7 days; they work on R2's S3 API domain, not a custom domain, and browser form `POST` upload is not supported. [R2 S3 setup](https://developers.cloudflare.com/r2/get-started/s3/), [R2 presigned URL details](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

Browsers enforce CORS for cross-origin signed requests; the signature alone does not bypass that browser check. Configure only the production web origin, methods, and headers that the upload/download uses. Native iOS/Android HTTP clients do not enforce browser CORS. R2 documents CORS for private presigned requests explicitly. B2's S3-compatible API supports bucket CORS configuration and signed uploads/downloads, but its S3 API does not support browser form `POST`. [R2 CORS](https://developers.cloudflare.com/r2/buckets/cors/), [B2 CORS](https://www.backblaze.com/docs/cloud-storage-cross-origin-resource-sharing-rules), [B2 S3 API limitations](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api).

**Tigris browser-CORS gap:** its presigned-URL guide says URLs can give temporary upload/download access to private bucket objects, and its S3 compatibility page lists signed PUT/GET and multipart support. Its separate [CORS guide](https://www.tigrisdata.com/docs/buckets/cors/) only describes configuring CORS for public buckets. I could not verify from current public docs that browser uploads/downloads to a **private** bucket work cross-origin. That needs provider confirmation or an integration test before relying on Tigris for the Next.js client; this does not affect ordinary native HTTP clients. Tigris's presigned URL docs also say that for buckets created after 28 September 2026, `x-amz-*` headers must be chosen before signing and sent unchanged by the client; an added unsigned header is rejected. [Tigris presigned URL requirements](https://www.tigrisdata.com/docs/objects/presigned/), [Tigris S3 API compatibility](https://www.tigrisdata.com/docs/api/s3/).

The upload limits are ample for ordinary personal documents. R2's upload guide advertises a 5 GiB single-part upload and multipart uploads up to 5 TiB/10,000 parts; the platform limits page gives a more precise multipart maximum of 4.995 TiB. Multipart parts are 5 MiB–5 GiB, and incomplete uploads auto-abort after seven days by default. B2 publishes a 10 TB maximum object size and multipart uploads (up to 10,000 parts; 5 MB–5 GB parts in its native API docs). AWS S3 supports 48.8 TiB objects and multipart uploads. Tigris documents multipart S3 operations, but I did not find a current official maximum object/upload size; do not assume AWS's maximum applies. [R2 upload limits](https://developers.cloudflare.com/r2/objects/upload-objects/), [R2 platform limits and units](https://developers.cloudflare.com/r2/platform/limits/), [B2 object-size comparison](https://www.backblaze.com/cloud-storage/comparison/backblaze-vs-idrive), [B2 large files](https://www.backblaze.com/docs/cloud-storage-create-large-files-with-the-native-api), [AWS S3 object limits](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html), [Tigris S3 API compatibility](https://www.tigrisdata.com/docs/api/s3/).

Provider-managed encryption at rest is available/documented for each: R2 encrypts objects and metadata with Cloudflare-managed AES-256 keys and uses TLS in transit; Tigris says encryption at rest/in transit is on; B2 supports Backblaze-managed SSE-B2 and customer-key SSE-C; S3 automatically encrypts new object uploads with SSE-S3. Server-side encryption is not end-to-end encryption: the storage service can still serve plaintext to a request authorized by its keys. B2 specifically warns that object names and metadata are not encrypted in a way that meets HIPAA protections; keep personal names, document types, and government identifiers out of bucket names, object keys, and metadata for every provider. If the provider must not be able to read a document, application/client-side encryption is a separate design decision. [R2 data security](https://developers.cloudflare.com/r2/reference/data-security/), [Tigris features](https://www.tigrisdata.com/features/), [B2 server-side encryption and metadata warning](https://www.backblaze.com/docs/cloud-storage-server-side-encryption), [S3 default encryption](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryption.html).

For EU storage, R2's `eu` jurisdiction is an explicit restriction and is immutable after bucket creation. B2's EU Central region stores account data in Amsterdam, costs the same as its other regions, and is also fixed at account creation. Tigris's default global placement follows access patterns; its docs offer EU geography/region configurations but not the same explicit jurisdiction terminology. AWS has regional buckets; the price illustration below uses US East solely to anchor a current published price. [R2 jurisdiction details](https://developers.cloudflare.com/r2/reference/data-location/), [B2 data regions](https://www.backblaze.com/docs/cloud-storage-data-regions), [Tigris regions](https://www.tigrisdata.com/docs/concepts/regions/).

## Illustrative monthly object-storage cost

| Case | Workload for one month | R2 Standard | Backblaze B2 | Tigris Standard | AWS S3 Standard |
|---|---|---:|---:|---:|---:|
| **A — initial** | 5 GB stored; 5 GB direct downloads; 1,000 uploads; 10,000 reads | **$0.00** | **$0.00** | **$0.00** | **$0.12** |
| **B — growth** | 100 GB stored; 100 GB direct downloads; 10,000 uploads; 100,000 reads | **$1.35** | **$0.63** | **$1.76** | **$2.23** |
| **C — large personal archive** | 1 TB stored; 500 GB direct downloads; 100,000 uploads; 1,000,000 reads | **$14.85** | **$6.88** | **$19.43** | **$55.23** |

Reproducible assumptions: the workload inputs mean decimal bytes (`1 GB = 10^9 bytes`, `1 TB = 1,000 GB`) held for the full month; each upload is one PUT and each read is one GET; there are no multipart parts, LIST/HEAD requests, retries, versions, or other operations; downloads go directly from the storage provider to users, not through a separately metered CDN/Worker; prices are USD before tax. R2's platform limits define GB as decimal; Tigris explicitly defines its GB as binary; AWS S3 explicitly defines storage GB as binary, so those two are converted from scenario bytes by dividing by `2^30`. For B2, the public price is per byte-hour but the published headline is per TB; the estimate assumes 1 TB = 1,000 GB for the rate conversion. AWS uses US East (N. Virginia), standard S3; its 100 GB monthly Internet allowance is assumed unused by other AWS services. The AWS page explicitly defines storage GB but not the Internet-transfer GB beside its rate; the estimate applies the same binary conversion to transfer. Actual invoices meter bytes and Cloudflare rounds usage to billing units, so treat these as illustrations rather than byte-exact quotes. [Tigris unit and averaging rules](https://www.tigrisdata.com/pricing/), [R2 rounding and GB/GiB rules](https://developers.cloudflare.com/r2/pricing/) and [R2 limits](https://developers.cloudflare.com/r2/platform/limits/), [B2 byte-hour billing](https://www.backblaze.com/cloud-storage/pricing), [AWS binary GB and price-list publication](https://aws.amazon.com/s3/pricing/) and [US East price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/us-east-1/index.json).

Math:

- **R2:** A uses 5 of 10 free GB-month and is within both request allowances. B: `(100 − 10) × $0.015 = $1.35`. C: `(1,000 − 10) × $0.015 = $14.85`. All three request totals are below 1M Class A/10M Class B; egress is free.
- **B2:** A uses less than 10 GB free. B: `(100 − 10) ÷ 1,000 × $6.95 = $0.6255`, rounded to $0.63. C: `(1,000 − 10) ÷ 1,000 × $6.95 = $6.8805`, rounded to $6.88. Each download amount is below 3× average storage, and standard object requests are free.
- **Tigris:** A's 5 decimal GB is 4.66 binary GB, inside the 5 binary GB, 10,000 A, and 100,000 B monthly allowances. B storage: `((100 ÷ 1.073741824) − 5) × $0.02 = $1.76`. C storage: `((1,000 ÷ 1.073741824) − 5) × $0.02 = $18.53`; uploads: `(100,000 − 10,000) ÷ 1,000 × $0.005 = $0.45`; reads: `(1,000,000 − 100,000) ÷ 1,000 × $0.0005 = $0.45`; total `$19.43`. Egress is free at these volumes.
- **AWS S3:** Storage uses AWS's binary GB. A: `(5 ÷ 1.073741824) × $0.023 + (1,000 ÷ 1,000 × $0.005) + (10,000 ÷ 1,000 × $0.0004) = $0.116`, rounded to $0.12; 5 GB egress is inside the 100 GB allowance. B: `(100 ÷ 1.073741824) × $0.023 + 10,000 ÷ 1,000 × $0.005 + 100,000 ÷ 1,000 × $0.0004 = $2.23`; 100 GB egress is inside the allowance. C: `(1,000 ÷ 1.073741824) × $0.023 + 100,000 ÷ 1,000 × $0.005 + 1,000,000 ÷ 1,000 × $0.0004 + ((500 ÷ 1.073741824) − 100) × $0.09 = $55.23`.

## Tigris current terms and document sensitivity

The current [Tigris pricing page](https://www.tigrisdata.com/pricing/) links its footer **Terms of Service** to [Tigris Service Agreement](https://www.tigrisdata.com/docs/legal/service-terms/). That is the relevant published link surfaced by the current pricing page. Its page metadata says “Last updated: December 26, 2024”; its docs footer separately carries a September 2026 bot-update marker, so the latter should not be treated as an agreement revision date. The older [site.tigrisdata.com agreement](https://site.tigrisdata.com/service-terms) is dated December 2023 and contains an extra restriction not present in the linked agreement; do not substitute that old text for the current linked page.

The current linked agreement says in §6.2 that a user may not **“provide access to, distribute, sell, or sublicense the Tigris Object Storage Service to a third party.”** Its §6.1 also licenses access “only for User’s internal use”; §4 says Enterprise Users may be permitted to invite End Users to access the service and Customer Content. The current §6.2 does not include the older 2023 sentence prohibiting use “on behalf of” or to provide a product or service to third parties. The interaction between internal use, the third-party-service prohibition, and ordinary app-user access to each person's private files is **unresolved**. This is not a legal conclusion; ask Tigris for written clarification if considering it.

For sensitive documents, the current agreement defines Prohibited Content to include Restricted Data. Its current Restricted Data definition includes GDPR Article 9 special categories, information protected by specified laws, and information that could otherwise be sensitive personal information under applicable privacy laws. The linked agreement text does not explicitly enumerate government ID numbers in the current definition, unlike the older 2023 page; the [current Data Processing Addendum](https://www.tigrisdata.com/docs/legal/data-processing/) says the service “is not intended to meet any legal obligations for any Sensitive data,” while the current pricing page advertises a HIPAA BAA as available. These statements leave the standard service's treatment of passports, driver's licenses, or other government IDs unclear. Ask Tigris which contract/plan applies and whether those files are permitted before storing them; do not infer either blanket permission or blanket prohibition from this research.

## Decision implications

For the first 1–10 GB, R2's published 10 GB-month free tier and no-egress pricing fit the stated workload, and its familiar S3-compatible TypeScript integration is the chosen trade-off. Its marketing says no card is required, but actual R2 setup requires subscription checkout and Cloudflare's billing docs require a primary payment method to purchase products, so confirm checkout requirements. B2 remains a useful comparison: it has 10 GB always-free, no minimum retention, EU Central storage, and a 3× download allowance. If files grow beyond the free tier, B2 is cheaper among these modeled storage charges, while R2's egress remains free and its bill is driven primarily by stored GB-month. Revisit the choice if usage, regional requirements, or pricing materially changes.

Tigris's no-card recurring allowance is attractive, and its global/S3-style interface is hosting-independent, but the private-browser CORS documentation gap, uncertainty around app-user access to private files, and sensitive-document terms should be checked before choosing it. AWS S3 remains the most familiar reference and avoids an S3-compatibility layer, but the modeled direct-download cost is much higher at the 1 TB scenario and current signup credits are temporary. In every case, enforce app-level ownership checks before issuing signed URLs and keep buckets private; a low storage bill does not provide application authorization or end-to-end confidentiality.
