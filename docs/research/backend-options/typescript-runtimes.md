# TypeScript runtime and metadata-backend options

Research checked **12 October 2026** against current vendor pricing and documentation. The working assumption is a personal FileTasks deployment for **1–5 people with 1–10 GB of File data**, low and intermittent API traffic, private documents, and modest relational metadata. Prices are public USD rates before tax. Free allowances and service limits can change; recheck the linked pricing pages before implementation. This is a comparison, not a stack decision or an ADR.

The root Next.js app can remain the web client. The backend option needs an HTTPS API contract usable by that client and by iOS/Android; it does not need to host the Next.js UI. File bytes should live in object storage, while the database keeps File records, Attachment relationships, and authorization metadata.

## Runtime fit and the existing server code

The current server uses [`node:sqlite` and `node:fs`](../../../services/api/src/database.ts), and its login flow uses [`node:crypto` `scrypt`](../../../services/api/src/auth.ts), an opaque bearer token, and an HTTP-only cookie. That can continue behind a full Node host with durable storage configured, but moving the server routes to Workers or Neon Functions is a backend migration. The Next.js web client can stay separately hosted and call an HTTPS API; iOS and Android can use the same JSON API and bearer credentials.

**Workers are a TypeScript-friendly isolate runtime, not a full Node server.** Workers use web platform APIs and support a subset of Node APIs. As of compatibility date 4 August 2026, Node compatibility defaults are enabled, but compatibility does not make the Worker a Node process. In particular, `node:sqlite` is a stub, and its writable filesystem is memory-backed and unique to a request, so it cannot hold FileTasks' durable database. D1 is the natural Cloudflare SQL replacement; it is SQLite-based and accessed through a Worker binding. [Node compatibility](https://developers.cloudflare.com/workers/configuration/compatibility-flags/), [`node:sqlite` stub](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#enable-nodesqlite-module), [Worker filesystem behavior](https://developers.cloudflare.com/workers/runtime-apis/nodejs/fs/), [D1 overview](https://developers.cloudflare.com/d1/).

Cloudflare documents `node:crypto` as supported apart from a few algorithms and functions, so the current `scrypt` import is not an automatic incompatibility. The practical issue is CPU: the Free Worker limit is 10 ms per invocation, and Cloudflare says heavier authentication workloads often use 10–20 ms. Measure the current password-hash parameters in a Worker before counting on Free; a sustained overrun terminates the request. The Workers Paid plan starts at $5/account-month and includes 10 million requests and 30 million CPU-ms/month; beyond those allowances, listed rates are $0.30/million requests and $0.02/million CPU-ms. [Cloudflare crypto support](https://developers.cloudflare.com/workers/runtime-apis/nodejs/crypto/), [CPU limits](https://developers.cloudflare.com/workers/platform/limits/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/).

A small Hono API is a reasonable TypeScript shape for Workers, but authentication remains app work unless a separate provider is added. Existing sessions could be represented in D1 and checked in handlers; alternatively, the API can validate an external JWT. Keep owner checks in the API before reading or writing a File record or issuing a file URL. A private bucket and signed URL control object access; they do not replace application-level authorization.

**Neon Functions are full Node.js handlers, not a hosted Next.js application.** Neon documents Node.js 24 handlers, a `pg` connection to the same branch and region, and injected `DATABASE_URL` credentials. That is a more familiar runtime for an independent TypeScript API, but the app still needs explicit routes and must not assume that Next.js API route files are automatically supported. A conventional Node container/VM remains the broadest compatibility option for Node modules and local development, though it brings host lifecycle and storage choices. [Neon Functions GA details](https://neon.com/blog/neon-backend-is-ga), [Functions overview](https://neon.com/docs/compute/functions/overview).

## Database and idle-cost fit

Task, Event, Occurrence, Recurrence rule, Reminder, File, and Attachment records have natural relationships and ownership constraints. Relational SQL makes foreign keys, transactions, owner-scoped queries, and joins straightforward. D1, Postgres on Neon, and Turso’s SQLite-compatible database can all hold this modest metadata; **none should hold the document bodies**. A NoSQL database such as DynamoDB can also serve the workload, but it asks the implementation to design partition keys and query indexes around known access patterns and often denormalize relationships instead of using SQL joins and foreign keys. The AWS comparison in [the AWS baseline](aws-baseline.md) covers that alternative.

### Cloudflare D1

D1 has no compute-hour charge: Cloudflare says queries are charged by rows read/written and storage above the plan allowance, and no charge applies while the database is idle. Free allows 5 million rows read/day, 100,000 rows written/day, and 5 GB total storage across the account. The separate per-database ceiling is 500 MB Free; paid permits 10 GB per database and includes the first 5 GB storage, then $0.75/GB-month. Paid usage includes 25 billion reads and 50 million writes per month, then $0.001/million rows read and $1/million rows written. These are **row-operation counters, not GB-month storage units**. Reads count scanned rows, so indexes matter. If Free daily read/write allowances are exceeded, D1 blocks queries until its 00:00 UTC reset; exceeding the storage cap blocks inserts or schema changes that grow storage. [D1 pricing and quota behavior](https://developers.cloudflare.com/d1/platform/pricing/), [D1 per-database limits](https://developers.cloudflare.com/d1/platform/limits/).

For small personal metadata, D1’s free storage and row allowances are ample. A design that moves File bytes into R2 avoids using D1's 2 MB row limit as an accidental attachment limit. D1’s SQL model fits the domain better than KV; KV can still be useful for caching or rate limits, but should not be the source of truth for task/file relationships.

### Neon Postgres and the newly GA backend

Neon Free currently lists 100 projects, 100 CU-hours/project/month, 1 GB Postgres storage/project and 20 GB total Postgres storage across the account, 10 branches/project, and 5 GB public network transfer/project/month. Free compute scales to zero after five idle minutes and that setting cannot be disabled. On Launch, the public docs list no monthly minimum (invoices under $0.50 are not collected), $0.106/CU-hour, $0.35/GB-month Postgres storage, and five-minute scale-to-zero by default. Paid plans include 500 GB/project public transfer before $0.10/GB; transfer is shared across Postgres, Object Storage, and Functions. [Current Neon plans](https://neon.com/docs/introduction/plans).

Neon Object Storage is S3-compatible, private-bucket capable, and integrated with branch semantics. Free includes 5 GB/project; paid object storage is $0.023/GB-month with no per-operation fee. Therefore, a 10 GB archive exceeds Free. Budget about **$0.23/month for 10 GB-month on a paid plan** if the paid rate applies to all 10 GB, plus any compute or usage beyond the plan allowances. Count stored GB-month separately from monthly downloaded GB: even on Free, Object Storage downloads share the 5 GB/project transfer allowance with the database and Functions. Current docs cap each object at 5 GiB, including multipart uploads. [Neon object storage pricing and plan allowances](https://neon.com/docs/introduction/plans#object-storage), [Object Storage overview and limits](https://neon.com/docs/storage/overview), [usage-based plan notes](https://neon.com/docs/introduction/plans#public-network-transfer).

Free Neon Functions include 10 active Capacity-Hours, 400 waiting Capacity-Hours, and 1 million invocations/month. Those Free allowances are enforced at both the organization total and per-project levels. Paid Launch rates are $0.10/active Capacity-Hour, $0.025/waiting Capacity-Hour, and $0.60/million invocations; billing stops between requests, but includes background `waitUntil` work. These quotas are separate from Postgres CU-hours. The complete Neon backend suite was announced GA on 17 September 2026, so as of this check it has roughly 25 days of GA history despite the vendor describing it as production-ready. [Neon plans and Functions billing](https://neon.com/docs/introduction/plans#functions), [GA announcement](https://neon.com/blog/neon-backend-is-ga), [scheduled Functions announcement](https://neon.com/blog/your-neon-functions-can-now-run-on-a-schedule).

### Neon Managed Better Auth: quota is attractive, topology needs a check

Managed Better Auth is included in Neon plans, with up to 60,000 MAUs on Free, and stores identity/session data in the `neon_auth` schema. The current authentication flow returns an `access_token` JWT and also sets an HTTP-only session cookie. However, Neon’s current roadmap explicitly says a **separately deployed frontend and backend is not yet supported**, because the managed HTTP-only cookie cannot be shared securely between domains. The roadmap also says Managed Better Auth is in active development; custom plugins/hooks are not all supported. For FileTasks, keep the existing bearer and cookie contract in view: validate native iOS/Android bearer handling and the separate Next client/API topology before relying on Managed Better Auth as a drop-in replacement. It is not enough to compare the MAU allowance. [Managed Auth overview and quota](https://neon.com/docs/auth/overview), [authentication flow](https://neon.com/docs/auth/authentication-flow), [current auth roadmap](https://neon.com/docs/auth/roadmap).

Neon’s current docs list Object Storage in AWS Frankfurt (`aws-eu-central-1`), among other regions, and say Functions run in the database’s region. Treat region availability as a deployment option, not as a complete EU-only processing guarantee; verify the service’s data-processing terms and what happens to authentication, logs, support access, backups, and API traffic before making a residency claim. [Neon Object Storage regions](https://neon.com/docs/storage/overview), [Neon Functions](https://neon.com/blog/neon-backend-is-ga).

## Private file upload and download path

For either Workers + R2 or Node + Neon Object Storage, use the same basic protocol:

1. The client asks the API for an upload. The API verifies the session and user ownership, creates an opaque object key, and records a pending File entry.
2. The API returns a short-lived signed `PUT` URL for that exact key and allowed content type. The browser or native app sends file bytes directly to the object store over HTTPS.
3. The client calls a finalize endpoint. The API checks that the object exists and that its metadata/size are acceptable, then marks the File as ready. Downloads use a fresh authorization check and a short-lived signed `GET` URL.

R2 documents presigned `GET` and `PUT` URLs for direct browser uploads/downloads; its Worker binding can handle server-side object operations. The signed URL is a temporary bearer capability, so keep the bucket private, restrict the operation/key/expiry, and configure CORS for the web origin. [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [R2 Worker binding](https://developers.cloudflare.com/r2/api/workers/workers-api-usage/), [R2 CORS](https://developers.cloudflare.com/r2/buckets/cors/). Cloudflare’s Free account request-body cap is 100 MB and Worker memory is 128 MB; direct upload avoids routing large documents through that API path. R2 presigned URLs use the S3 API domain and do not work on a custom domain. [Worker body and memory limits](https://developers.cloudflare.com/workers/platform/limits/), [R2 presigned URL limitations](https://developers.cloudflare.com/r2/api/s3/presigned-urls/).

Neon Object Storage supports private buckets, S3-compatible signed `GET` and `PUT` URLs, and browser-side uploads; it requires path-style addressing for S3 clients, and bucket access level is configured through Neon rather than S3 ACL/policy writes. Use the Neon API/SDK to issue a URL only after checking the File owner. Object Storage is available in Frankfurt, but Free storage is 5 GB/project and the current per-object limit is 5 GiB, so confirm those limits against actual expected file sizes. [Neon storage overview](https://neon.com/docs/storage/overview), [presigned upload/download guide](https://neon.com/docs/storage/objects#presigned-urls), [S3 compatibility details](https://neon.com/docs/storage/s3-compatibility).

## Scheduled Reminder work

A single scheduled job can scan an indexed `Reminder` due-time field, claim due rows idempotently, and enqueue or deliver notifications. Email/SMS delivery itself may have separate provider charges. Cloudflare Cron uses UTC expressions and supports every-minute schedules. Free accounts allow five Cron triggers and 10 ms CPU per trigger; paid Cron allows 30 seconds when scheduled more often than hourly and 15 minutes at hourly-or-less frequency, with a 15-minute wall-time ceiling. Queue can add retry handling, but Free Queues retain messages for 24 hours and include 10,000 operations/day; a typical delivered message uses three operations. For one personal reminder sweep, a simple Cron plus an idempotent database status is likely enough. [Cron schedule rules](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [Cron CPU/limits](https://developers.cloudflare.com/workers/platform/limits/), [Queues pricing and retention](https://developers.cloudflare.com/queues/platform/pricing/).

Neon Function Triggers provide branch-scoped cron schedules that work while the database is scaled to zero, avoiding a `pg_cron` job that would require the database to stay active. A scheduled Function can query due Reminder rows and send or enqueue the work. Keep this job idempotent and monitor the Function Capacity-Hour and invocation quotas above. [Neon scheduled Function Triggers](https://neon.com/blog/your-neon-functions-can-now-run-on-a-schedule).

## Conventional Node hosting

A full Node host is the least surprising choice for native Node libraries and existing `node:sqlite` development patterns, but free plans often make the database or filesystem unsuitable for durable storage:

- **Render Free** sleeps after 15 minutes without traffic and takes about a minute to wake. Its free web-service filesystem is ephemeral, so local SQLite data is lost on sleep, restart, or deploy; Free services also cannot attach persistent disks or run one-off jobs. Free Postgres is 1 GB but expires after 30 days, then is deleted after a 14-day grace period. That tier can host a sleepy stateless API with an external durable database and object store, but it is not a durable local-database host. [Render Free limits](https://render.com/docs/free).
- **Railway Free** provides $1/month of usage credit and a maximum 0.5 GB volume. Its $5 one-time trial grant lasts up to 30 days; Hobby has a $5/month base and includes $5 resource usage, then charges the delta. Volumes are $0.15/GB-month. This can host a conventional Node service, but the free volume is far below the 1–10 GB document target, and the $1 credit is not a promise of a free always-on service. [Railway plans and usage prices](https://docs.railway.com/pricing/plans), [trial terms](https://docs.railway.com/pricing/free-trial).
- **Fly.io** currently offers two total VM hours or seven days of trial access, whichever comes first. Apps stop when the trial ends unless billing is configured; do not count it as a long-term free tier. [Fly.io trial](https://docs.fly.io/about/free-trial).

Use these as runtime hosts paired with a remote database and private object storage if Node familiarity matters more than a single integrated provider. Render Free’s cold start and Railway’s ongoing subscription/credits should be compared with the idle behavior and total storage limits of the database/object-store combination, not treated as a complete backend price by themselves.

## Other current TypeScript choices

**Turso** is the closest current hosted option to the existing SQLite data model. The current pricing page lists Free at 5 GB storage, 500 million monthly rows read, and 10 million rows written; Developer is $5.99/month with 9 GB included and $0.75/GB overage when overages are enabled. The page says idle databases cost only storage. Metadata for this personal app should fit Free comfortably, but Turso provides no document bucket in this plan comparison, so pair it with R2/B2/S3 or another object store. Treat its 2 October Supabase acquisition as product-roadmap context: Turso says the service and open-source development continue, while deeper integration is expected. [Turso pricing](https://turso.tech/pricing?frequency=monthly), [Turso acquisition announcement](https://turso.tech/blog/turso-is-joining-supabase).

**Deno Deploy** is an optional idle-friendly TypeScript runtime, but not a complete relational-plus-file backend. Its current Free plan lists 1 million requests/month, 20 GiB egress, 10 CPU-hours, 1 GiB Deno KV, and idle app shutdown after roughly 20–30 seconds; it does not include relational SQL or object storage. Pro is $20/month. Deno announced that it is joining Cloudflare, so its near-term product direction is also in transition. It would still need a separate relational database and object store, which weakens its case here. [Deno Deploy pricing](https://deno.com/deploy/pricing).

## Infrastructure as code

Cloudflare’s native deployment path is **Wrangler** with TypeScript Worker code and `wrangler.toml`/`wrangler.jsonc` bindings for D1, R2, and Cron. Cloudflare also maintains an official Terraform provider; Pulumi offers a TypeScript Cloudflare provider if infrastructure definitions should remain in TypeScript. [Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/), [Cloudflare Terraform](https://developers.cloudflare.com/terraform/), [Pulumi Cloudflare provider](https://www.pulumi.com/registry/packages/cloudflare/).

AWS CDK is TypeScript but synthesizes AWS CloudFormation and models AWS resources; it is not a general multi-cloud abstraction for Cloudflare. CDK remains the direct AWS option described in the [AWS baseline](aws-baseline.md). CDK for Terraform was deprecated and is no longer maintained as of 10 December 2025, so it is not a good bridge for this choice. Neon offers its own TypeScript `neon.ts` configuration and CLI for declaring Neon services; that is provider-specific rather than a universal IaC layer. [AWS CDK resource model](https://docs.aws.amazon.com/cdk/v2/guide/resources.html), [CDKTF release/deprecation](https://developer.hashicorp.com/terraform/cdktf/release), [Neon `neon.ts`](https://neon.com/blog/introducing-neon-ts).

## Remaining checks before implementation

The largest decision-sensitive unknowns are expected monthly download volume (especially for Neon’s shared Free egress quota), maximum individual File size, whether the existing `scrypt` hash fits Worker Free CPU, and whether Managed Better Auth can satisfy the separate frontend/API and native-client contract without a same-origin proxy. For EU residency, verify the precise processing and backup terms in the chosen provider’s current agreement rather than relying only on a region selector.
